# Trzy role: admin / technik / pracownik

| | |
|---|---|
| **Status** | zaakceptowana (właściciel, 2026-11-02) |
| **Źródło** | plan `docs/aegis/plans/2026-11-02-przepisanie-aplikacji-serwis.md` |

## Kontekst

Stara aplikacja miała tylko konto w tabeli `users` bez ról; nowy pracownik wymagał ręcznego SQL.

## Decyzja

Macierz uprawnień w enumie `Role`. Pracownik ma pełny zakres operacyjny — przyjęcie, edycja, status, zdjęcia, wyszukiwanie, **wydanie laptopa**, **zmiana ceny i kosztu**, anulowanie. Technik ma dziś identyczny zakres (rezerwa na przyszłe funkcje). Admin dodatkowo zarządza kontami.

## Konsekwencje

Jedna linia w `Role::abilities()` dodaje uprawnienie. Testy pokrywają macierz dla każdej roli. Uwaga: plan w F-56 wspomina „anulowanie tylko przez technika/admina”, a sekcja 5.3 i D9 dają anulowanie pracownikowi — realizacja idzie za D9, sprzeczność odnotowana w raporcie parzystości.
